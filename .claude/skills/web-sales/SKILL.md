# Web制作営業リサーチ

入力: $ARGUMENTS

このSkillは親セッションで実行する。新規v4 runでは`SPEC-v4.md`を全体仕様とし、`schemas/workflow-v4.md`、`schemas/data-model-v4.md`、`schemas/worker-handoff-v4.md`、`schemas/outreach-guide.md`を読む。旧v3 runでは旧`SPEC.md`、`schemas/workflow.md`、`schemas/data-model.md`、`schemas/worker-handoff.md`を読む。両版の営業理由の判定基準は`schemas/proposal-opportunity-review.md`を正本とし、採用・文面化・レビュー前に適用する。利用者に工程ごとの再指示を求めず、保存済み段階から再開する。外部へのメール・DM・フォーム送信はしない。

## 入口

- 新しい地域・業種・Segmentなら`init`で新規runを作る。既存runの続きが指定されたら、そのrunだけを`resume`し、新規探索を指示されていない限り探索を繰り返さない。
- 旧v3 runは既存の営業判断と送信履歴を維持する。新しい選定基準を既存runへ自動適用しない。利用者が再評価を依頼した場合は、元データと送信履歴を保全し、影響を確認してから進める。
- 旧v3 runは`qualification.status`を持たないため、`qualification-worker`とv4の`pursue`ゲートを通さず、v3の保存状態からOUTREACHへ進める。営業理由の妥当性と営業禁止の確認は両版で同じ基準を使う。
- UI上の工程は`DISCOVER → TRIAGE → QUALIFY → OUTREACH`。活動、サイト、営業判断、連絡可能性、実送信結果は別のデータ軸である。

## DISCOVER

`discovery-worker`で通常Web、地図、媒体、地域・駅名、業種言い換えの基本探索を終えてから追加探索する。`import`が重複除去と新規件数を記録する。少数件や固定件数だけで止めず、探索飽和・利用者上限・技術上限を区別する。この段階で求人、料金、全チャネルの連絡先を深掘りしない。公式サイト未発見は`unconfirmed`。

## TRIAGE

全発見事業者を浅く確認する。地図・公式サイトと、サイト確認済みならトップのdesktop/mobile証拠を基本とし、下層ページやSNSを全件で読まない。`triage-worker`は`activity`、`website.presence`、`web_gap`、既存の`lead.status`、視覚証拠を別々に返す。閉業・対象外など明確な根拠だけを既存のhard exclusionとし、不明や視覚失敗だけで除外・`recheck`にしない。確実な重複は`merge-duplicates`で統合し、除外扱いにしない。

## QUALIFY

一次判定で`triage.decision=advance`とした候補だけを`qualification-worker`へ渡す。Segmentに合う情報源を選び、同じURLの再取得と全文の受け渡しを避ける。観測事実は出典・確認日時・確認範囲とともに`evidence[]`へ保存し、未確認を否定事実に変えない。制作予算・外注意欲を推測しない。商業シグナルや開業・求人等のtriggerは優先度の材料で、機械的な必須条件ではない。

`qualification.status`は`pursue | watch | drop`。`pursue`は確認済みの事実と既存手段との差に基づく「提案の芯」と、その相手に意味のある新規・改善価値が説明できる場合だけ。詳しい判定は共通の正本に従う。判断を左右する一点が未確認なら、確認対象・再開条件・再確認日を付けて`watch`とし、今回の文面生成から外す。確認不能だけで恒久的な`drop`にせず、同じ取得を繰り返さない。`P1/P2/P3`は`pursue`内の営業順で、根拠不足を救済しない。

## OUTREACH

詳細な文章窓口探索は原則`pursue`だけに行う。既に見つけた窓口は再利用する。公式の文章窓口が1件使えれば探索終了。見つからない場合だけ既定の5チャネルを根拠付きで確認し、未確認・アクセス制約が残れば`contact_unverified`、全件不在確認後にのみ`phone_only`/`contact_not_found`とする。

文面生成の直前に`node scripts/web-sales-store.mjs plan-drafts --run <DIR> [--limit <今回作る件数>]`を実行する。既定では優先順の10件だけを表示する。親は返された`selected`のIDだけを`outreach-worker`へ渡し、今回送る見込みに合わせて件数を選ぶ。残りの候補はEvidence・資格判定・窓口を保存したまま、文面を先に量産しない。送信済み・過去送信判明・営業見送り・利用可能な文章窓口なし・既存文面あり等は文面作成前に止める。再開時も既存文面を無条件に作り直さず、レビューまたは理由の再評価へ回す。未仕分けの送信チェックがあれば先に`settle-queue`する。

`outreach-worker`は選ばれたIDの保存済みEvidenceから提案の芯の各差分を再確認し、成立しなければ文面を作らず資格判定へ差し戻す。文章生成で弱い提案を救済しない。`review-worker`は理由と本文を独立に確認し、`schemas/outreach-guide.md`の4つの失敗型も見る。文章窓口や理由がなければ文面・送信キューを無理に作らない。制作例は提案に合う1〜3件を選び、本文を字下げしない。

送信キューは`pursue`、公式文章窓口、営業理由`ready`、文面`reviewed`、未送信・利用可能な送信先をすべて満たす事業者のみ。送信後の店舗チェックは`sent`、窓口を使えなかった場合の「送信不可」はチャネル単位の`unable`、事業者への営業を見送る「営業見送り」は事業者単位の`lead_skip`として区別する。複数同時にチェックしない。過去の`unable`理由を自動で`lead_skip`に読み替えない。`lead_skip`と送信済みは別窓口を含めキューへ戻さず、明示的な`lead_reopen`のみ見送りを解除する。`unable`の後、別の確認済み窓口があれば通常のキュー再生成時にそちらを提示する。

利用者が送信チェックを保存した後、仕分けだけを求めた場合は`node scripts/web-sales-store.mjs settle-queue --run <DIR>`で対象と不備を事前確認し、問題なければ同コマンドに`--apply`を付けて確定する。旧形式の送信不可警告が出た場合は理由の意味を確認し、営業理由不足・営業お断り等の事業者単位の判断を窓口不可として確定しない。必要なら旧行に「営業見送り」欄を追加し、チェック先を修正する。このコマンドは探索・候補再選定・キュー補充・市場summary再生成をしない。未チェックは残す。`summarize`は全成果物を再生成するため、単なる仕分けには使用しない。未仕分けチェックがある間は`summarize`もその他の再生成処理も停止するので、先に`settle-queue`を行う。実送信日時を確認できない場合は`occurred_at=null`のままとし、今回チェックされた送信数と当日実送信数を混同しない。

旧形式の「送信不可」行は、通常の`--apply`では安全のため停止する。その理由が本当に窓口だけの不可であると確認できた場合のみ`--allow-legacy-unable`を追加する。営業そのものの見送りならこのフラグを使わない。

`reviewed`は文面レビュー時点の状態であり、実際の送信を承認した印ではない。人が送る直前には、営業理由を支える現在のメニュー・予約導線・営業禁止表示と送信先の用途を、変動し得る箇所だけ確認する。理由が失効したらその文面を差し戻す。文面への違和感や宛先不一致を、実送信エラーを意味する「送信不可」に記録しない。
文面だけの差し戻しは`outreach.status=generated`、`reviewed=false`、`review_note`を`import`してキューから外す。過去に送信済みと判明したときは、実送信日時と記録日時を混同せず`record-outcome --result previously_sent --reason <確認根拠>`を使う。送信済み履歴の原文を消さない。

## 保存・報告

各バッチ後に保存状態を読み直す。最後に`summarize`と`validate`を実行し、発見、一次判定、追加調査、`pursue`、文章窓口、レビュー、送信キュー、実送信を別々に報告する。partialは完了と装わず再開地点を示す。workerはファイルを書かずJSONLを返す。単純な集計と状態管理だけのためにworkerを起動しない。

次のリスト作成では、文面作成を始めた件数、レビュー差し戻し件数、キューへ入った件数、人が「そのまま送れる／短い修正／全面改稿／送れない」と判定した件数と主な理由を同じバッチで記録する。未送信や過去文面を今回の品質評価に混ぜない。成功条件は、弱い提案を文面生成前に止めつつ、意味のある小規模改善・Growth提案を誤って落とさず、生成文面が調査報告型・指導型・無価値提案型・汎用テンプレート型にならないこと。件数の少なさだけで成功としない。

候補の見送り理由は個別事業者の判定記録、「送信不可理由」は窓口が使えなかった記録、「営業見送り理由」は営業を進めない利用者判断の記録である。これらはSkillの自己修正指示ではない。実行中にSkill・Agent・schema・保存スクリプトを自己判断で編集しない。利用者からの改善フィードバックは別途扱い、旧runへ自動適用しない。
