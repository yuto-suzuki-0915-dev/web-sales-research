# Web制作の初回営業文を作る

入力: $ARGUMENTS

このSkillは親セッションで実行する。公開情報をその場で言い換えるだけで営業文を作らず、保存済みの調査根拠を確認してから文章化する。文面の規約とA/B/C判定は `schemas/outreach-guide.md` に従う。

## 1. 対象と既存leadを解決する

1. URL、事業者名、所在地から、`research/leads/` をGlob/Grepして同一事業者のleadを探す。全lead本文を読み込まない。
2. 同名別店舗を混ぜない。名称だけでなく所在地、公式URL、公式SNS、運営主体などを照合する。
3. leadパスが入力された場合は、そのファイルを正本として読む。存在しないパスや対象不明を推測で補わない。

## 2. 文面化できる根拠があるか確認する

次を確認する。

- `depth: 詳細監査` で、同定・現在性・公開チャネル・顧客導線・反対仮説が扱われている。
- 営業ビューに調査判定、営業アクション、提案タイプ、最小改善案、次の確認がある。
- 営業文に使う固有事実が、S-ID付きのF-IDとして直接確認されている。
- 主要なサイト、サービス、導線の根拠が `schemas/research-guide.md` の鮮度目安と今回の目的に照らして使える。
- G1〜G5、または未充足・不明の理由が記録されている。

初期確認だけ、固有事実がない、主要根拠が古い、情報が矛盾している、対象同定が弱い場合は、そのleadだけでA/Bを出さない。

## 3. 必要な場合だけ既存Auditを実行する

leadがない、または文面化に必要な根拠が不足・陳腐化している場合は、新しい調査方式を作らず既存のAuditを使う。

1. `.claude/skills/audit-lead/SKILL.md` のworker向けモード方針を読む。
2. `schemas/research-workflow.md` に従い、親がWeb検索前にAudit runを作成・再読する。
3. `research-worker` に指定1社の詳細監査を委任する。親自身はWeb検索せず、workerへファイル保存を依頼しない。
4. `schemas/research-handoff.md` の返却を検証し、親がleadとrunを保存・再読する。
5. 保存後のleadだけを使って営業文を作る。

外部取得ができず根拠不足のままならCとし、推測で営業文を埋めない。既存leadが十分なら新しいrunを作らない。

## 4. A/B/Cと営業方針を決める

`schemas/outreach-guide.md` のゲートを使う。既存の有望/保留/除外、営業アクション、提案タイプを尊重するが、機械的な置換はしない。

- A: 活動中の事業者に既存公式サイトがあり、現在の具体的不足と、軽微改修、リニューアル、または再構成を外部から提案する合理性が残る。
- B: 活動中で、公式サイトが確認範囲で見つからないか実質的な受け皿がなく、既存媒体を残した新規サイト/LPの役割が具体的に説明できる。
- C: 上記の根拠が不足する、現状維持・情報修正・自己修正で十分、サイト品質が十分、営業中を確認できない、または営業理由が一般論に留まる。

情報修正や軽微改修が最小提案で、外注する合理性が弱い場合は、全面リニューアルへ膨らませずCにする。営業アクションが追加確認ならA/Bとして見せない。調査判定が保留でも営業アクションが営業候補の場合は、未充足のGが今回の最小提案を損なわないとlead内で説明されている場合だけA/Bを検討する。

## 5. 初回営業文を作る

AまたはBのときだけ作る。F-IDで裏付けられた事業者固有の事実を1文だけ使い、相手の欠点を直接批判しない。推測I-IDや不明U-IDを事実のように書かない。

営業文は150〜300文字程度を目安にし、次の順にする。

1. 簡潔に名乗る。
2. 相手について確認した固有事実を1つ示す。
3. その事実から、連絡理由を未来側の表現でつなぐ。
4. デザイン、実装、公開まで対応できると伝える。
5. `schemas/outreach-guide.md` の制作例を掲載する。
6. 制作例を見ることを中心にした軽いCTAで終える。

管理画面URL、技術スタック、過剰な称賛、売上・集客の保証、初回からの打ち合わせ要求は入れない。予約機能は必要性が根拠から確認できる場合だけ「対応可能」と短く触れる。

## 6. 根拠を最終照合して出力する

文章化の後に、個別文と判定理由をleadのF/Sへ戻して照合する。根拠にない表現は削除する。営業文内にF-IDや出典リンクは入れないが、判定理由と個別事実にはF/S参照とURLを付ける。

出力は次の6項目とする。

```markdown
## 1. 営業対象判定
A / B / C

## 2. 判定理由
- 3〜5項目。F/S参照と出典リンクを付ける。

## 3. 営業に使える個別事実
- 1〜3項目。F/S参照と出典リンクを付ける。

## 4. 推奨する営業方針
- 提案タイプと、前面に出す価値を原則1つ。

## 5. 営業文
150〜300文字程度の1案。

## 6. 個別化した部分
営業文のうち、この事業者専用にした一文を引用する。
```

Cの場合はセクション5を「今回は営業文を生成しません。理由: ...」とし、セクション6は「なし」とする。情報不足によるCは、事業者の質が低いと断定せず「現時点では営業優先対象にしない」と表現する。

このSkillは草案を表示するだけで、メール、DM、問い合わせフォーム、SNSなどへ送信しない。送信は人間の別判断と明示依頼を必要とする。
