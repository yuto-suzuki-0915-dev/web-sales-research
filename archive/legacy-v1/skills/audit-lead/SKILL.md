# 1事業者のAudit

モード: Audit。入力: $ARGUMENTS

このSkillは親セッションで実行する。`schemas/research-workflow.md` を読み、親がrunを保存・再読してから指定1社の詳細監査を `research-worker` に委任する。親自身はWeb検索しない。workerは `schemas/research-handoff.md` の形式で返し、親がleadと台帳を保存する。既存leadがなくても実行できる。事業者/店舗を一意に同定できなければ、不足を確認してから進める。

## worker向けモード方針

- 事業・商品/サービス・公表価格と実際の客単価の違い、スタッフ/拠点、Maps、口コミ、SNS、外部予約媒体、現在のサイトを確認する。
- 流入元 → 情報確認 → 比較検討 → 問い合わせ/予約、を整理する。公開リンクの存在と、利用者が実際に通る経路は分ける。
- サイトの問題を先に決めず、顧客が何を決める必要があるかから調べる。具体的な不足と、既存チャネルで解決できている部分を両方記録する。
- サイト不要、問題がWebの範囲外、小改修/媒体整備で十分、制作済み/制作中、集客の受入余力がない可能性を公開情報で検証する。不明は不明のまま残す。
- 必要な場合だけ近い競合を少数参照する。競合がサイトを持つことを必要性の根拠にしない。
- 最後に Demand / Redesign / Value Gap を証拠がある分だけ分類し、共通ゲートで有望/保留/除外を判定する。複数分類も該当なしも可。

既存の有望判定も見直す。再調査では現在の主要根拠を再確認し、変更点・反証・判定履歴を保持する。最小改善案・営業アクション・提案タイプ・次の確認は共通の `schemas/research-guide.md` と返却契約に従う。workerは選別済みの保存用データを親へ返す。親は保存後、ユーザーに短い要約と保存先のみ伝える。
