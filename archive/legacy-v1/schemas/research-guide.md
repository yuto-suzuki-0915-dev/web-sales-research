# 調査・判断・保存の共通規約

保存の実行者は常に親セッション。workerはここで定める証拠・判定・再利用の規約で調査し、`schemas/research-handoff.md` の形式で返す。親は `schemas/research-workflow.md` に従いrun/leadを保存する。以下の「保存」「更新」は親の責務を指す。

## 1. 実行範囲

依頼条件をrunに明記する。未指定値はCLAUDE.mdの既定値を用いる。「20件」は初期確認する事業者の上限であって有望数ではない。既存結果を再利用する対象もこのバッチ上限に含め、既存除外を見つけるたび無制限に補充しない。Auditは1社。広い依頼もまず上限内の1バッチを調査し、残りの範囲を保存する。

標準の打ち切り目安はrun全体で検索クエリ12本（同じ検索の再実行も使用回数に数える）、初期確認は1社3ページ程度、詳細監査は1社10ページ程度。worker1回は初期確認最大3社/詳細監査1社に分け、最初の初期確認は1社だけ返して親の保存を確認する。これは調査資源の上限目安であり判定条件ではない。重要な矛盾の解消に必要な追加確認は理由とともに記録する。検索が枯れた場合やアクセス制約で進まない場合は件数未達のまま終える。初期確認だけで根拠不足の候補は保留。詳細監査の枠を使い切っても有望に繰り上げない。

## 2. 証拠の扱い

- **観測事実 Fxxx**: 直接開いて確認した内容。出典 Sxxx と確認範囲を必須にする。「公式ページにXと記載」は観測できるが、Xが現実に正しいことまで確認したとは限らない。
- **推測 Ixxx**: 根拠Fxxx、そこから導く仮説、成立条件/反証条件を付ける。顧客への摩擦、事業価値、想定導線は通常こちら。
- **不明 Uxxx**: 確認できない事項、確認できない理由、判定への影響、次に確認する方法を書く。取得失敗もこちら。
- **出典 Sxxx**: 正確なURL、媒体、確認日時、公開/更新日（不明可）、取得方法、取得状態を記録する。時刻を取得できなければ `YYYY-MM-DD（Asia/Tokyo、日付精度）` とし、時刻を作らない。日時が取れるときはタイムゾーンを付ける。イベント日と公開日を混同しない。

原則は公式サイト/発表、公式SNS/採用/予約ページ、Mapsや媒体の事業者ページ、第三者情報の順に当たる。公式アカウントの同定根拠も記録する。重要な矛盾や古い情報は独立した別ソースで確認する。転載記事が複数あっても独立した裏付けとは限らない。

検索スニペットは発見の手掛かり。本文未取得の主張を確定事実・有望判定の唯一の根拠にしない。ログイン/アクセス制限/JavaScript依存/自動取得失敗を、サイト不在、閉業、リンク切れ、予約不具合と同一視しない。本文未取得でもURLと取得失敗は出典に残せるが、その中身をFとして作らない。

「存在しない」「古い」「分かりづらい」は確認ページと方法を示して範囲を限定する。視覚や操作上の問題は実際にそれを確認できる手段が必要。テキストしか見ていない場合は未検証とする。外部フォームの送信・予約確定・テスト問い合わせは行わない。

レビューの件数/評価、SNSフォロワー数、メニュー価格は観測値。実顧客数、現在の流入量、平均客単価、利益、LTV、予算に変換しない。公開メニューに基づく価格帯/想定利用額は算式と選択条件を明記して推測に置けるが、実平均客単価とは呼ばない。ROIや増客数の試算は標準では不要。依頼があって試算する場合も仮定と売上/利益の違いを明示し、判定の証拠には使わない。

ページ全文の大量保存はせず、判断に必要な短い要約・URL・確認範囲を残す。口コミ投稿者など営業判断に不要な個人情報は収集しない。

## 3. 詳細監査の観点

次を確認済み/不明/非該当に分ける。空欄を憶測で埋めない。

1. 同定と事業: 商号/店舗名、所在地、運営主体、営業中/開業予定の根拠、サービス、対象顧客、公開価格、スタッフ/拠点。SNS更新がないだけで休業としない。
2. 公開接点: Maps、口コミ、SNS、外部予約媒体、サイト、採用ページ。各URLの同定、更新/確認時点、接点としての役割を整理する。
3. 意思決定: 顧客が何を確認して次の行動を選ぶか。公開リンクで確認した経路と、実際の流入/離脱の仮説を分ける。
4. 不足: 具体的なページ・情報・導線、不整合、顧客への影響仮説。利用者に重要な理由を当該事業に結び付ける。
5. 事業価値: 情報確認、比較説明、紹介後の信用確認、予約前の不安解消、法人問い合わせ、採用など、Webが担う役割を1〜3個に絞る。
6. 反対仮説: 現状で十分、媒体整備/小改修で十分、Web外の課題、制作済み/制作中、本部一括管理、受入余力不足等から、その候補に最も強いものを実際の公開ページで確かめる。支持証拠・反対証拠・未確認点を残す。単なる「可能性あり」の列挙で完了しない。
7. 提案範囲: 現状維持、既存媒体整備、小改修、新規ページ/サイト、全面刷新を比較し、必要最小の範囲を選ぶ。運用担当・更新負担・既存予約の利点・移行や二重管理の負担も考える。費用が不明なら投資回収を断定しない。

低単価だけで除外せず、高単価だけで有望にしない。低単価でも説明の反復や多数のメニューが重要な場合はある。見込み客接点の強さと、支払能力/意思は別物。事業活動の未確認と、閉業の確認も別物。

## 4. 共通判定ゲート

タイプは重複可。該当根拠がなければ未確定/該当なし。探索モードと結果のタイプが違っても隠さず記録する。

- Demand: 現在有効な事業変化/明示需要と、なお残るWeb上の役割不足。
- Redesign: 既存公式サイトと、顧客の判断/行動に関わる具体的な改善点。
- Value Gap: サイト有無より先に確認した事業/接点のシグナルと、既存チャネルで満たされない情報確認の役割。

有望は以下を**すべて**満たす。加点式や「2項目あれば合格」にしない。

| ゲート | 必要な根拠 |
|---|---|
| G1 同定・現在性 | 同一事業者と、現在の活動または有効な開業予定の証拠 |
| G2 課題・機会 | 特定のページ/チャネルで観測できる未充足の役割。サイトなし単独は不可 |
| G3 事業との接続 | 当該顧客の比較/判断/行動と、改善する意味を結ぶ証拠と仮説 |
| G4 適切な改善範囲 | Webで対処可能で、媒体整備/現状維持と比較した最小提案に合理性がある |
| G5 反証・現在の余地 | 最も強い反対仮説を調べても提案理由が残る。決定的な未確認は解消または保留 |

- **有望**: 詳細監査を行いG1〜G5を満たす。予算/支払意思は不明でもよいが、その不明を隠さない。最小提案が有償の小改修なら有望にできるが「全面刷新が必要」とはしない。
- **保留**: 決定に必要な根拠が不足、主要情報が取得不能、情報が矛盾、未監査、予算枠ではなく調査上限で未完等。何が分かれば判定が変わるかを指定する。
- **除外**: 根拠を伴って現状/媒体整備で十分、事業価値に見合うWeb改善がない、Web外の問題、対象条件外、閉業確認等。欠測だけを除外理由にしない。詳細監査前でも明確な対象外は除外可。

除外は当該調査条件での判断であり永久評価ではない。優先順位は課題の具体性、意思決定への重要性、現在の契機、根拠の確かさ、最小改善の負担を説明して付ける。細かな点数で偽の精度を作らない。

### 調査判定・営業アクション・提案タイプは別軸

調査判定（有望/保留/除外）とG1〜G5は従来どおり維持する。営業アクションは人間が次に何を優先するか、提案タイプは検討する改善の範囲を表す。調査判定から機械的に変換しない。

| 営業アクション | 判断の意味 |
|---|---|
| 営業候補 | 現在の公開根拠から、特定の改善を提案する合理性を人間に提示できる。連絡の実行は人間が決める |
| 追加確認 | 具体的な問題/価値仮説があり、営業判断の前に重要事項を1〜数点確認する必要がある。判定不能時の安全な既定値でもある |
| 見送り寄り | 現在の確認範囲では問題が小さく、現状維持/事業者自身の簡単な修正で十分という根拠がある。追加調査の優先度は低い |
| 営業対象外 | 本部一括管理、業種違い、閉業確認など、今回の対象単位/条件で営業の合理性がない。根拠が推測なら明記し、永久除外にしない |

「保留 = 営業できない」ではない。保留でも、具体的な問題がある追加確認と、現状維持が有力な見送り寄りは区別する。保留のまま営業候補とする場合は、未充足のGが何か、その不明が今回の最小提案の合理性を損なわない理由を明記する。肝心の事実や外部支援の合理性が未確認なら追加確認とし、営業候補というラベルでG判定を迂回しない。営業アクションの変更だけでstatusやGを変更しない。

提案タイプは **情報修正 / 軽微改修 / 部分リニューアル / 全面リニューアル / 新規サイト / LP / なし**。第一候補を1つ選び、必要なら代替候補を別記する。情報修正は料金・営業時間・住所などの文言/媒体間整合、軽微改修はCTA変更・既存ページへの情報追加・PDF情報のHTML化など。部分/全面リニューアルは一部/全体の再構成、新規サイトは新しい受け皿、LPは特定サービス等の説明・行動を受けるページを指す。目的が確認できなければ「なし」にする。

**最小改善原則:** 「Web上に問題がある = リニューアルを売る」ではない。料金修正、営業時間統一、CTA変更、既存ページへの追記、PDFのHTML化、媒体間の情報整合で足りるなら情報修正/軽微改修を優先する。部分/全面リニューアルは、それらでは観測された問題を十分に解決できない理由を示せる場合だけ候補にする。新規サイト/LPにも必要な役割の根拠を求める。自己修正で十分という反対仮説と、外注する合理性は分けて検討する。

保留でも条件付きの最小改善案と次の確認は記載してよい。提案タイプは発注や連絡の推奨ではない。「見送り寄り＋情報修正」も成立する。根拠が足りない場合は営業アクションを追加確認、提案タイプをなしとし、一般的な改善案を捏造しない。見送り寄りには現状で足りる支持材料、営業対象外には当該条件での理由を必ず付ける。

各leadに調査判定、営業アクション、提案タイプ（第一候補/内容/代替候補）、営業アクションの理由、次に確認すること、最小改善案、サイト改善不要の反対仮説を持たせる。理由・条件・反証は既存のF/I/U/Sへ対応させる。情報修正であっても、どの料金/住所が正しいか未確認なら正解を決めつけない。営業候補以外にも次の確認欄を持たせ、不要なら「現時点で追加確認なし」、低優先なら再調査条件を記す。

## 5. 同定・永続化・再利用

### 一つの事業者レコード

保存先は全判定共通の `research/leads/<lead-id>.md`。判定が変わっても移動しない。Grepで名前、旧名、URL、所在地、Maps URL/識別子等を探し、一致したレコードだけReadする。初期確認で除外した事業者も最低限の記録を残す。

lead-idは英小文字・数字・ハイフンで地域と名称/店舗を組み合わせる（例 `osaka-kita-example-umeda`）。作成前に同一性とパスの未使用を確認する。同名別会社は別ID。同一店舗の改名/URL変更は既存IDに別名を追記する。ドメインだけでは同一企業/店舗と決めない。チェーンは今回の対象単位（法人/ブランド/店舗）と親事業者を明記し、同一単位を重複計上しない。親子の関係は参照パスで残す。同一性が決められないときは保留にし、独断で統合しない。

必須の最低記録はID・同定情報・判定・理由・証拠/取得制約・最終実調査日・再調査条件・run-id・履歴。初期確認では詳細欄を「未監査」で省略できる。詳細監査では全セクションを埋め、不明/非該当には理由を書く。

営業ビューの追加項目は初期確認/再利用でも省略しない。旧leadに項目がなければ、既存証拠から付与し、付与日と「Web再取得なし」を記録する。元のstatus、G1〜G5、F/I/U/S、人間のメモ、last_researched_atは変えない。新しい公開情報を見ていないので調査件数も増やさない。今回のように既存runへの追記が明示的に依頼された場合は、営業ビューだけを冒頭に追加し、元の台帳・件数・state・調査日時を維持する。

### 再利用と鮮度

既存leadをまず読み、条件と証拠が今も使えるか評価する。鮮度の初期目安は需要イベント/募集30日、サイト/サービス/導線90日。これは当プロジェクトの運用目安であり事実の有効期限の保証ではない。予定日や締切が近い、変更を示す情報がある、利用条件が変わった、人間が再調査を指定した場合は期間内でも対象の事実だけ再確認する。

除外も同じ規約で見直す。「期間内だから絶対除外」「期間を過ぎたから全て再調査」としない。前の除外理由を覆す条件を調べ、関連箇所だけ更新する。再利用時は当時の確認日を保持し、新たにWebを見ていないのにlast_researched_atを今日にしない。古い根拠を検証できないまま使う場合、そのrunでは保留とする。今回の実調査で結論が変わればlead正本も更新する。

F/I/U/SのIDはlead内で固定し、別内容に使い回さない。変化した事実は新IDを付け、旧事実を過去情報と明示する。更新履歴に前判定→新判定・変更理由・根拠ID・runを追記し、人間のメモ/営業判断を上書きしない。再利用のみでは履歴を無意味に増やさず、run側に参照を残す。

### runと中断

run-idは `YYYY-MM-DD-<mode>-<scope>-01`（日付はJST、modeはdemand/redesign/value-gap/audit、scopeは英小文字・数字・ハイフン）。Globで既存パスを確認し、同名なら末尾を02、03と増やす。`research/runs/<run-id>/summary.md` に条件、台帳、件数、状態、停止理由、次の行動を保存する。保存完了したrunは変更せず、再調査は新runに元runへの参照を残す。

中断したrunの再開は同じsummaryを読み、記録済み部分を再利用して続ける。leadにはlast_runを残す。lead保存後・台帳更新前の中断は、last_runが一致するleadをGrepして台帳を復旧する。逆に台帳のファイルがなければ保存失敗として修復する。多重実行で他の書込が見えたら更新を止め、親へ知らせる。これは運用ルールでありファイルロックの実装ではない。

検索だけで発見した未着手名はrunの未着手欄にのみ残してよい。個別ページへのアクセスを試みた対象は保留でもleadを保存する。検索語と重要な行き詰まりだけrunに残し、全文ログはため込まない。

## 6. 件数と完了条件

run台帳は1対象1行、処理区分は新規調査/再調査/既存再利用のいずれか。同一runの初期確認から詳細監査への移行は同じ行を更新する。前の呼出で新規作成したleadは、そのrun内では新規調査のまま。呼出回数や調査段階を事業者数に加算しない。今回判定と正本判定が違う場合（古い有望を未再検証で保留等）は両方と理由を書く。

- 今回調査N = 新規調査A + 再調査B（個別公開ページの確認を試みた対象数）。
- 対象総数T = N + 既存再利用C = 有望P + 保留H + 除外R（このrun時点の判定）。
- 詳細監査DはNの内数。再利用した過去の詳細監査をDに加えない。
- 検索結果の件数、重複、未着手はTに含めない。該当タイプが複数でも1件。

台帳に当時の判定、理由、根拠ID/当時の確認日、leadへの相対パスを残す。上位表示数と有望総数を混同しない。表示外も全件保存する。

summaryの先頭（frontmatterの後）は短い営業ビューとし、その後に詳細台帳を残す。営業ビューの確認件数はT（今回調査N＋既存再利用C。再利用があれば内訳も表示）、詳細監査はD。営業アクション4区分の合計はTで、各対象を1回だけ数える。表は営業候補・追加確認を優先して最大5件、表示外の件数と詳細台帳/leadへの参照を残す。0件なら「営業候補・追加確認なし」。新規runでは全対象台帳の当時の理由欄にも営業アクションと提案タイプの第一候補を併記し、表示外の対象も当時の判断を残す。調査判定のP/H/Rは従来の詳細結果に保持する。営業ビューはそのrun時点の判断で、後日leadが変わっても過去runを黙って同期しない。

合意した上限まで実施または検索が枯れ、必要な保存・整合確認が終わればcomplete（保留や有望0件でも可）。ツール/保存失敗や作業中断で予定工程が残ればpartial。実行中断でrunningのまま残る場合も再開対象とする。完了前に実在ファイル、台帳の一意性、件数式、重要な証拠参照、反証、営業理由を確認する。営業理由は「観測したXから、顧客のYを確認しやすくするZに検討価値がある」という検証可能な仮説に留める。
